# 馬大別忙 · 設計決策

> 2026-10-02 與 Hans 逐項確認。來源：church-staff-pwa（self-host 版）改版為多教會代管服務。

## 產品

- 代管、多教會共用的**同工工具**（不含會友）。單一 App「馬大別忙」（驚嘆號可有可無），教會 logo 在 App 內顯示。
- 平台：iOS、Android、Web（PWA），同一份 Flutter code。
- 語言：i18n 架構（ARB），目前繁中、簡中、英文、日文、韓文（日文、韓文照用語表翻譯後直接上線，有懂的人看過再修）。預設跟隨系統：照手機或瀏覽器的偏好語言清單，用第一個支援的，都不支援用英文（`app/lib/core/languages.dart`，對應規則在 `testdata/languages.json`）；中文標明簡體，或來自中國、新加坡、馬來西亞又沒標明繁體的是簡中，其他中文都是繁中。「設定 → 語言」可以自己選，存在帳號。App 另外把實際顯示的語言寫進 `users/{uid}.appLocale`，給後端寫推播用。後端寫的字照各自對象的語言（`functions/src/languages.ts`）：推播照**收到的人**的 `appLocale`，沒有就繁中；邀請頁和教會的 manifest 照瀏覽器的 `Accept-Language`，對應規則和 App 一樣（教會頁本身人人同一份，讓 CDN 存著，由頁面自己的程式在瀏覽器換語言）；新教會的預設聚會和服事項目照建立者的語言，之後是教會自己的，不跟著別人變；驗證信、重設密碼信照 App 當下的語言；CSV 匯出照匯出的人的語言。聚會名稱、服事項目這些教會自己打的字原樣照送。用語照 `docs/i18n-glossary.md`；每份翻譯檔的條目要和繁中一樣（`test/app/translations_test.dart`）。英文的日期一律寫月份（Oct 18），不用 10/18；日文、韓文照 CLDR 的寫法（10月18日(日)、10월 18일 (일)），和 App 裡一樣。主畫面圖示下的名稱只放當地名稱（馬大別忙、马大别忙、Martha, sit、マルタ、ひと休み、마르다의 쉼표），照手機或瀏覽器的語言，App 不支援的語言用英文：Android 在 `res/values*/strings.xml`，iOS 在 `Runner/*.lproj/InfoPlist.strings`（相機、照片權限的說明也在這裡），網頁版在 `web/manifest*.json`，由 `web/index.html` 的程式挑；教會頁的主畫面名稱照教會的設定（`CONTEXT.md`〈主畫面名稱〉）。這些名稱都要和 `functions/src/languages.ts` 的 `appName` 一樣（`functions/test/languages.test.ts`）。網頁版的中日韓字型由瀏覽器的語言決定（Flutter 照 `navigator.language` 挑 Noto Sans TC／HK／SC／JP／KR），不是 App 顯示的語言；開頁預熱上次在這台裝置顯示的語言和瀏覽器的語言，兩個不同時兩個都預熱（帳號的語言可能在別台裝置改過，或沒登入）（`app/lib/core/fonts.dart`）。各語言自己的名稱（简体中文、한국어）等首頁畫好才預熱（開的就是語言頁時例外）：引擎把同一批下載的字型照檔名排先後，簡中、韓文排在繁中前面，一起抓的話繁中的「？」「！」會變成它們的樣子。
- 營運：Hans 個人。不主動拓展，有人問就給用；已知有台灣、香港、馬來西亞詢問。
- 發布：**全部做完一次發布**，不分階段。
- 用語：一律說「安排服事表」，不說「排班」。其他用語見 `CONTEXT.md`。
- 介面風格：乾淨、少操作、少文字。原則見 `docs/design-principles.md`，以 Apple Human Interface Guidelines 為準。

## 後端

- Firebase Blaze（用量維持在免費額度內），設 budget alert。
- Cloud Functions 放特權邏輯；Web 放 Firebase Hosting；**移除 Cloudflare**。
- 專案：`prod`、`dev` 兩個新 Firebase 專案。不沿用 `church-staff-pwa`。
- Region：`asia-east1`，所有教會共用。
- 資料模型：
  - `users/{uid}`：全域個資、語言、推播 token（每裝置）
  - `churches/{cid}/members/{uid}`：角色、權限群組、牧區（沿用現有 user doc 的權限形狀）
  - `churches/{cid}/...`：rosters、settings、staff_orders
- 遷移預留（輕度）：repository interface 保持乾淨；`churches/{cid}` 可整棵匯出；ID、時間不依賴 Firestore 專有型別；權限邏輯另寫規格文件。
- 多教會身分：一個人可以在好幾間教會。「設定 → 切換教會」切換，也在這裡輸入邀請碼加入或建立另一間（例如在 A 教會服事、幫 B 教會開一間）。

## 帳號與教會

- 自由註冊。
- 登入方式：
  - **Google 登入為主**，第一版就支援。登入按鈕照 Google 和 Apple 的品牌規範（見 `docs/design-principles.md`），Android 和網頁放第一個，iPhone 放在 Apple 之後。
  - 原生 App 用系統的帳號選擇（Android Credential Manager、iOS Google Sign-In）。裝置做不到時（手機沒有 Google 帳號、Play 服務太舊）改走瀏覽器登入，並在 Crashlytics 記一筆非當機錯誤：Firebase 沒登錄這台的簽章 SHA-1 時，看起來也是「沒有帳號」，要靠這筆紀錄發現。設定錯誤（client ID 錯）和使用者取消不改走瀏覽器。
  - iOS 加 **Sign in with Apple**（Apple 準則 4.8：有第三方登入就必須提供）。這個功能要付費的開發者帳號才能設定，所以在 M7 付年費後補上。
  - email＋密碼收在下方，用 email 註冊的人才需要驗證 email；Google、Apple 帳號視為已驗證。
  - Firebase Auth 開「同一 email 只能有一個帳號」，處理不同登入方式的帳號連結（`account-exists-with-different-credential`）。
- 同名檢查：名稱正規化（空白、全半形、大小寫）後完全相同就提醒並擋下，附聯絡連結。被搶註時由 Hans 在後台處理。
- 不設教會數量或用量上限；非教會單位也可使用（服務條款寫明為教會設計）。
- Hans 的後台：教會改名、轉移管理員、停用教會。
- 教會 logo：管理員上傳到 Firebase Storage，上限 1MB，壓成 512px，只在 App 內顯示（頂部、歡迎畫面）。Storage rules 只允許該教會管理員寫入。
- 退出教會：非管理員可以自己退出。
  - 入口放在「設定 → 教會資訊」最下方，紅字。
  - 確認視窗：「退出〈教會名〉？需要重新邀請才能回來」，要再按一次「退出」。不要求輸入教會名稱。
  - 退出後通知該教會管理員。
- 「設定」（第四個分頁，2026-10-19 前叫「我的」，網址還是 `/me`）：照常用程度排。自己的名字在最上面，點進去是「帳號」：名字、Email、登入方式、登出、刪除帳號（像 iPhone 的 Apple 帳號頁）；管理員接著是「管理教會」（同工、邀請、服事設定）；再來是通知、切換教會、教會資訊，語言、支持；最後是「LINE 社群」（有問題好找，客服與教會之間交流都在那裡）和「關於馬大別忙」（目前版本、檢查更新、隱私權政策、服務條款）。少用的收在下一層，外層才不會長；其他少用的設定在「教會資訊」。
- 開 App：載入完淡入首頁（約 0.25 秒），登入、歡迎、教會停用、開啟通知這些階段之間，和從教會網址、邀請連結打開的頁也一樣，不像打開一頁那樣從右邊滑進來；在這些頁上再打開一頁時，照平台的方式讓開（iOS 往左滑）。手機設了減少動態效果就直接換。
- 照片匯入：服事表右上角寫字「照片匯入」，不只放圖示（沒有一看就懂的圖示），字放大到 1.5 倍就不再放大，留位置給標題；還沒排過任何人的聚會，「開始安排」下面也有「用照片匯入」。
- 帳號刪除（Apple 5.1.1(v)）：App 內自行刪除，刪 Auth、`users/{uid}` 與所有 membership；服事表保留姓名文字；還有別人的教會，唯一管理員須先交接；只有自己一個人的教會跟帳號一起刪除（和刪除教會一樣，30 天後清掉），還沒加入教會的人在歡迎頁也能刪除；教會刪除後保留 30 天可還原。

## 功能（第一版）

- 核心：登入、同工、服事表。
- 安排服事表時選人：
  - 沿用 self-host：只列出有這項服事的同工，照同工排序排好。
  - 加搜尋框，搜尋整間教會的成員，比對名字的一部分，忽略全半形與大小寫。
  - 結果分兩區：上面是「排過{服事項目}的人」，下面是「其他同工」。管理員選了下面這個聚會的同工，直接把這項服事加到他身上，不問：排過一次，下次就列在上面，所以不用先到同工頁設定每個人的服事。新加的人照同工排序排在最後。選了不是這個聚會同工的人（例如來支援的），只排這一次；他會列在聚會頁的「排過○○的服事，還不是同工」，負責人按「加為同工」才算（#82）。不是管理員的人沒有權限改同工，選了也只排這一次。
  - 還沒有人排過時，上面不是空的一區，而是列出所有同工，並說「排過一次，下次就會列在上面」（非管理員看到「還沒有人負責…」）。
  - 名單用久會變長，有人也會不再服事：管理員按「編輯」可以拖曳排序，也可以按減號把人從名單移除；移除的人回到「其他同工」，一樣搜得到、排得到，這一天已經排的不變；只有移除時跳「已從…名單移除…・復原」。選了又取消的人不加進名單。非管理員只能「調整順序」。不做「很久沒排就自動拿掉」：一年一次的服事（例如聖誕節獻詩）會被誤拿掉。
  - 名單超過 30 人時，搜尋框自動取得焦點。
- 推播：FCM（iOS 需 APNs）。
- 夜裡不推播：服事表異動的推播在教會當地 22:00–7:00 不送，等 7:00 再送，而且只說這段時間對這個人淨變了什麼（排進又移出就不說；他自己改的、匯入的也不說）。外部通知不等，那是教會自己的。「設定 → 通知」的服事表異動寫明這件事。
- 服事提醒（#69）：各教會當地晚上 7 點發送（每小時整點跑一次，挑當地剛好 7 點的教會；#73），同工在「通知」選時間：**每週一晚上**（預設，一則列出週一到週日的服事）、前一天晚上、兩個都要（週一只發每週那則，裡面已經有隔天）。發送時間固定，不給管理員設定。推播的寫法照舊 PWA 的 n8n 提醒：標題是問候加上哪一段的服事（「平安 王小明，這週的服事」「平安 王小明，明天的服事」，名字用同工資料上的，沒有名字就寫「平安，這週的服事」），內容一天一行（「10/25（週日）主日崇拜 司琴、招待」）；標題不寫日期，日期在每一行。服事表異動的推播不加問候。
- 加入主畫面（#68）：App 是設計成加到手機主畫面來用的，iPhone 也只有從主畫面打開才收得到通知。手機瀏覽器裡加入或建立教會後，先顯示「加入主畫面」的步驟（iPhone：分享 → 加入主畫面 → 從圖示打開、再登入一次；Android Chrome 有安裝視窗時一鍵安裝），可以「稍後再說」。這一頁一定在那間教會的網址上：不是的話先重新載入 `/c/ID?to=/add-to-home`，主畫面才會是教會的名稱和圖示。首頁一直提醒到從主畫面打開，或在這台關掉為止。iPhone 在 Safari 的「通知」頁說明要先加入主畫面。各瀏覽器有各自的步驟（附截圖）；LINE 等 App 內的瀏覽器先教複製教會網址、改用手機的瀏覽器打開。電腦和商店版不顯示。
- 行事曆：Google OAuth。M7 買網域後送 Google OAuth 驗證（`calendar.events` 是 sensitive scope，不需要 CASA，免費）；通過之前是 **In production 但未驗證**（只有管理員連接日曆時會看到警告畫面，終身約 100 位授權者上限）。Google 登入只用基本權限，不會出現警告。管理員連接並選日曆；refresh token 加密存後端；讀寫皆由後端代理並快取；授權失效時顯示重新連接。手機 App 在 App 上方的瀏覽器頁面（iOS SFSafariViewController、Android Custom Tabs，Google 不准用 WebView）打開授權，結束時停在 `/calendar-done.html`（說已連接、請回到 App）；App 看到連接成功就關掉那一頁（iOS 可以，Android 的 Custom Tabs 不能由 App 關，要自己按 ✕）。網頁版還是在原分頁授權，回到 `/me/calendar`。從哪裡開始的寫在 OAuth state 的第一個字（`a` 手機 App、`w` 網頁），過期了也知道要回哪裡。Scope：`calendar.events`、`calendar.calendarlist.readonly`。
- 交換服事：由能安排服事表的人操作。在服事表上點某人 →「交換」→ 只列出同一服事項目的其他日期 → 點一下完成，兩天一次寫入，可復原。同工自己發起交換請求之後再做。
- 特別活動：貼在某一天服事表上的彩色標籤（聖餐、浸禮、特會…）。各聚會別的常用選項與顏色和服事設定放在同一頁，安排服事表時可勾選或臨時自訂。
- 開啟通知（#80）：不做開場教學。商店版和電腦上加入或建立教會後，這台還沒問過通知權限的話，先顯示一頁「被排到服事時通知你」：按「開啟通知」才跳系統的允許視窗，「稍後再說」直接到首頁；每台只出現一次。手機瀏覽器走加入主畫面，不顯示這頁。之後首頁一直有「開啟通知」，到開了或在這台關掉為止；手機上拒絕過的（系統不會再問）改成「到系統設定開啟通知」，「設定 → 通知」也有，打開這個 App 的通知設定，回到 App 就重新檢查。「設定 → 通知」還沒問過權限時開關都顯示關，按其中一個才跳系統的允許視窗；允許了只開按的那個，其他維持關（不是一次全開）。
- 活動的服事表（#60、#62、#63）：單次或不定期的活動（聖誕晚會、退修會、每月禱告會）就是行事曆上的活動，服事表掛在活動上，不屬於任何聚會。只有連接行事曆的教會能用。管理員和所有 roster-editors 可以安排，不看牧區；所有同工在活動頁看得到。名稱、日期以行事曆為準，活動改了服事表跟著改，刪了就取消；在 Google 日曆直接改的，後端一天核對三次（含提醒前的 18:30）。只有在建立時那本行事曆上確定讀不到，才算刪除；換了行事曆、授權失效都只暫停。重複活動的某一天換了 id（改「這個和後續的活動」）會接回同一天的新活動，安排時預設帶上一次的服事項目。整個活動一張服事表，照開始那天提醒，改期會通知被排到的人。
- 照片辨識：Hans 付費，Vertex AI 上的 Gemini（不拿資料訓練）；每教會每月 30 張；全站每月上限 US$20，超過自動關閉。第一次按「拍照」或「選照片」時先問一次：照片和同工名單會送到 Google 的 Gemini，「同意並繼續」才送（App Store 5.1.2(i)：個資送給第三方 AI 前要在 App 裡說明並取得同意）。同意記在帳號（`users/{uid}.photoAiConsentAt`），換裝置不再問；三個平台都問。「進階」複製指令、貼 JSON 不經過我們送資料，不問。
- LINE 通知、每日靈糧：由外部通知與教會連結取代（#41）。平台不直接串 LINE，外部通知交給 n8n 之類的工具轉發；教會連結可以填每天自動更新的內容來源。
- 身分與群組（#82、#83）：權限都從身分來，同工頁只有「身分」一區：管理員、牧者（全教會，或某幾個聚會）、行政、聚會負責人、事工負責人，每個下面寫一句能做什麼；一般同工什麼都不用選，下面寫「同工：看所有服事表和活動」。預設一個，「再加一個」。只有管理員能給身分；管理員不能拿掉讓自己還是管理員的那一個。
  - 管理教會 →「聚會與事工」：每個聚會和事工一頁，列負責人、同工（「加入同工」可以從全教會選人）、「排過○○的服事，還不是同工」（旁邊「加為同工」，朗讀時唸「把張志豪加為敬拜團同工」）。同工旁邊有「移出」（朗讀「把張志豪移出敬拜團」），按了就移出、可復原，不另外確認；負責人只看得到一般同工旁邊的「移出」，有身分的人只有管理員能動。「移除同工」只指移出教會。身分旁邊也是「移除」按鈕，一樣可復原。這些小按鈕用灰底（`RowButton`），不用強調色。管理員在這裡新增事工、改名、勾它連到的服事項目（各聚會的服事項目分開勾）、指派負責人、刪除事工（可復原）。
  - 不是管理員的負責人，「設定」多一區「我負責的」，直接開他的聚會或事工頁；他可以加入、移出一般同工，看得到全教會的同工名單。
  - 事工負責人在服事表上只點得動他的服事項目，其他的照常顯示；新增服事項目只能選他的，不能自己打；不能改特別活動、不能調同工排序。照片匯入只留他的服事項目、只能合併，沒有「取代當天全部安排」。寫入經 `editLedDuties`，由後端確認只改了他的服事項目。
  - 服事表分頁照牧區、負責的聚會和事工連到的聚會顯示，管理員和行政看全部。
- 小組：同工在每個牧區的小組名稱，是同工資料的文字欄位（`zones[].smallGroups`），在同工頁編輯與顯示、隨匯出與搬家保留。不做小組範本，也不用在權限或安排服事表（self-host 也只拿來顯示）。

### 與自家教會正式版對齊（2026-10-11）

比較基準是竹圍靈糧福音中心正式站實際部署的 self-host `main@ed9aab0`（build 235），不是公開安裝版。原則：補教會實際要完成的工作，不照搬舊畫面或舊實作；新版只有一種格式與流程，**不做舊版相容的 fallback**，舊資料在搬家時一次轉好。

- 匯入：照片和 JSON 進同一個可編輯的預覽，可改日期、服事項目、人名、活動；能安排該聚會服事表的人都能貼 JSON（收在「進階」）。「進階」也能複製照片辨識用的同一份 AI 指令（`photoPrompt`，後端依教會設定組出，不算照片額度），自己用其他 AI 讀照片，再把回覆整段貼上，前後的 ```json 和說明文字會略過。指令裡有同工名單，貼到哪個 AI 由使用者決定。名字只自動對到唯一且完全相同的同工；縮寫、相近、同名都要人確認，或明確保留為「無帳號」，不猜 uid。預設合併（只換提到的服事項目），「取代當天全部安排」要另外選，套用前顯示差異，可復原；預覽跟著最新的服事表更新，套用時資料和畫面上的不同就拒絕，請重新檢查。管理員可以在預覽順手把缺的服事項目、常用活動加進設定；照片上排到某項服事、但不在那項名單上的同工，管理員按套用時直接加進名單（和選人一樣，不另外問；服事設定裡沒有的服事項目不加），匯入的「復原」也一起拿回；非管理員匯入不改名單。活動顏色只收 0–5 的色票。
- 服事設定：常用活動可以改色、調順序。刪掉設定裡的選項不會清掉已安排的服事表；改名要同步未來的服事表時，另外預覽、明天起的才改、可復原，不改過去。服事項目改名經 `editService`，同工牧區與排序一起改。
- 無帳號的名字（#86，以前叫「外請」；很多只是還沒裝 App 的同工）：選人時列出這個服事項目排過的無帳號名字；點名字的「移除未來的安排」先預覽再套用、可復原，不動同名但連到帳號的同工。誰是誰只看 uid（見 data-model）。
- 服事表範圍：滾動顯示接下來約三個月，「顯示更多」再往後；已存的更遠服事表照樣顯示。不分季。
- 小組與回報人數（#85）：聚會頁有「小組」一區，管理員和那個聚會的負責人、牧者可以「新增小組」、改名、關閉、指派小組長。小組頁第一區有「小組長」一列（只有一位，點了從同工裡選，選別人就換人，也可以取消指派），下面是同工；小組長在「設定」的「我負責的」找到它。「管理教會」有「回報人數」開關，預設關。開著時，小組頁多「聚會時間」（每週或隔週幾，小組長也能設），聚會頁和小組頁多「人數」一區：「暫停聚會一段時間」（選哪一天恢復聚會；暑假、過年）、最近 12 週每次聚會的人數或「未填」「沒聚會」，點了補填。當天 21:00 還沒人填就推播給負責人（聚會的負責人、小組長，不給牧者）；首頁的「填寫人數」也只給他們，到下一次聚會為止。填的時候寫總人數和備註，或按「這次沒聚會」。
- 行事曆的歸屬與篩選（#84）：活動屬於全教會或某個聚會、事工。新增、編輯活動時多一列「屬於」：管理員和行政可以選全教會或任何群組，負責人只能選自己負責的（只有一個就不顯示這列）。負責人點自己群組的活動進編輯，點全教會或別的群組的只看內容；群組的活動在內容裡寫「敬拜團的活動」。負責人可以排自己群組活動的整張服事表。右上角篩選：跟我有關的（全教會的、我所在或負責的聚會和事工的、我被排到服事的活動）、全部、全教會、某個聚會或事工；管理員和行政預設「全部」，其他人「跟我有關的」，每間教會在這台裝置記住。月曆格子也照篩選。群組活動不推播。
- 行事曆：可編輯活動說明、複製活動（新的活動，不帶重複規則或服事表）。活動的開始、結束像 iPhone 的行事曆：點日期在那一列下面展開月曆，點一天就選好收起（選年份只換到那一年的月曆）；點時間展開滾輪（5 分鐘一格；原本的時間不在 5 分鐘上就 1 分鐘一格），時間跟著轉；一次只開一個，開的時候收起鍵盤、捲到看得到；結束下面寫活動多長。打開結束時間時活動不到一天，轉的是開始之後第一個那個時間（早於開始就是隔天）；一天以上的活動結束日不變。首頁顯示最近三個還沒結束的活動，共用行事曆既有的資料，不另外快取。
- 行事曆的月曆：點一天，下面只列那天的活動（跨好幾天的也算），標題寫日期；沒有就寫「這天沒有活動」，能編輯行事曆的人多一列「新增活動」，日期已經填那天。再點同一天、換月份或收起月曆，就回到整個月的列表。右上角收起、展開月曆時，月曆約 0.25 秒摺起、展開，不是一下子不見；減少動態效果時直接換。
- 時區（#73）：每間教會有自己的時區，從 16 個城市選（`functions/src/timeZones.ts`，App 是 `domain/church_time.dart`，兩邊的夏令時間規則用 `testdata/time_zones.json` 對過）。今天、換日、活動時間、月份分組、提醒、每日內容來源都照教會的時區，與後端一致，不看手機所在地；手機的時差跟教會不同時，行事曆和活動旁邊寫「教會當地時間（城市）」。建立教會時照建立者手機的時區（不在清單裡就找同時差的城市，找不到用台北），管理員在教會資訊改（同工看得到），改之前確認一次（使用者決定，不用復原）；聚會的服事表日期不跟著動，活動的服事表跟著活動在新時區的日期，不發通知。活動同步照當地 6:30、12:30、18:30（每小時跑）。統計、雲端費用、刪除教會滿期清除這些平台自己的排程維持台北時間。
- 每日內容：只收一種 JSON（見 data-model）。抓不到或不是今天就說明原因，管理員可以重抓；不顯示舊內容或固定連結代替。
- 外部通知：維持 HMAC 簽章的 webhook。舊 LINE 接收端（n8n 用 `x-notify-secret` 檢查）要改成驗 HMAC 才收得到；不另開舊的驗證方式。
- 搬家：保留小組與「關掉服事提醒」（舊 `weeklyRosterReminder=false` → 新的 `reminder` 靜音）。推播 token 不搬，換專案後在新 App 重新允許通知。舊服事表沒有 uid 的，用一次性的補 uid 工具（預設只預覽）。
- 復原：「復原」是真的寫入，成功才顯示「已復原」，失敗會說；批次修改與復原都比對當時的資料，別人改過就整筆拒絕，不覆蓋。服事表、同工設定（名字、角色、群組、牧區）、服事設定（單一聚會或整個清單）都一樣；同工自己的通知設定不算在同工設定的比對裡。
- 改了馬上顯示：服事表、同工、服事設定、通知設定按下去畫面就是新的，標題列寫「儲存中…」，寫入成功才出「已更新・復原」；寫不進去就變回原樣並說原因。寫入照舊是連線時的比對寫入，一次送一筆：接著改的那一筆等前一筆寫完才比對，所以連續修改不會被自己擋下（`app/lib/data/echoing_church_data.dart`）。寫進去了但伺服器的資料跟畫面不同（別人剛好同時改），最多 5 秒後換成伺服器的。行事曆活動也是按下去月曆就是新的（新增、修改、刪除），存不進去就變回原樣並說存檔失敗；伺服器回答後換成 Google 日曆存下的樣子，同一個活動連續改了好幾次，就等全部回答後整個月重讀（`app/lib/state/calendar_months.dart`）。邀請、教會資訊、連結、外部通知、照片匯入這些要等伺服器回答（新邀請碼、抓到的內容）的，照舊等寫完才顯示。
- 離線：只能看，不能改。網路斷了顯示「離線唯讀」，寫入直接說無法連線，不排隊、不在連線後補送。行事曆可顯示之前讀過的月份並標明「離線資料・資料讀取於…」，依帳號、教會、日曆隔離，失去權限或登出就清掉。
- 行事曆先顯示再更新：有網路時也先顯示這台裝置上次讀到的月份，同時重新讀；讀到了就換上，讀不到才標出這是上次的資料、什麼時候讀的。行事曆分頁顯示一個月時，先讀好前後兩個月。
- 平台後台也先顯示再更新：教會列表、教會的成員、統計、雲端費用都先顯示這台裝置上次讀到的，同時重新讀（`state/saved_read.dart`）。只存給目前登入的帳號，登出或換帳號就清掉；沒有權限或東西不在了也清掉。顯示的是上次的資料時，改費用、設管理員、點進教會要等讀到新的才能按，免得照舊資料改；扣回退款填的是訂單編號，不受影響。重新讀失敗（包括改了之後讀回來失敗）就標出這是上次的資料、什麼時候讀的，旁邊有「重試」，重試成功前一樣不能改。其他會等函式的地方不這樣做：待加入的教會、邀請預覽、還沒加入的教會頁要即時的答案，照片額度不擋畫面。
- 雲端函式先叫醒：閒置的函式第一次呼叫要多等約 3–4 秒。會呼叫函式的頁面一打開就先送一個不做事的呼叫（`{warmup: true}`），例如活動編輯、單一聚會設定、時區、照片匯入、輸入邀請碼、建立教會、平台後台（統計、雲端費用、教會成員）；同一個函式 5 分鐘內只叫一次。還沒有讓函式常駐（`minInstances`，每個每月約 US$8）。
- 網頁版更新：「設定 → 關於馬大別忙」顯示目前執行的版本；檢查更新只下載並驗證新版，按「更新並重新開啟」才換，編輯或儲存中不換、不自動重新整理。首頁只快取啟動必要的檔案，延後載入的頁面用到才下載；舊版發布的檔案保留。原生 App 從商店更新。
- 不做：自訂 AI 辨識提示詞、管理員代設別人的帳號密碼、季度切換、完整備份還原與修改紀錄。

- 支持頁的品項只顯示金額，並排成按鈕（字放大到排不下才一個一行）：同一種支持同名、只差金額，所以不用商店傳來的名稱（商店的各語言名稱審過之前會傳預設語言）。每月的寫「NT$30／月」，正在付的方案打勾、不能再買。App 圖示只有每月支持者看得到：支持頁一列「App 圖示」，點進去四款並排選；其他人只在「每月支持」下方看到一句「每月支持者可以換 App 圖示」，不放看得到按不到的選項。

  - 規格：綠界開發者網站（developers.ecpay.com.tw）的產生訂單（?p=2862）、檢查碼機制（?p=2902）、付款結果通知（?p=2878）。程式在 `functions/src/fundingEcpay.ts`，檢查碼機制頁的範例是它的測試。
  - 流程：支持頁選金額（50、100、200 或自訂 30–1,000 元）→ `POST /support/pay`（Hosting 轉到 `ecpayStart`）→ 後端記一筆待付款的訂單（只有金額和時間），回傳簽好 CheckMacValue 的表單（`ChoosePayment=ALL`，用 `IgnorePayment` 只留信用卡和 Apple Pay）→ 瀏覽器把表單送到綠界的付款頁 → 付款完成後綠界在背景 POST 到 `ecpayNotify`（綠界叫它 ReturnURL，要回 `1|OK`），付款人的瀏覽器經 `ecpayReturn`（綠界叫它 OrderResultURL）回到 `/support?paid=1`（網址裡沒有付款資料）。
  - 語言：支持頁把自己的語言帶給 `ecpayStart`，綠界付款頁的語言（`Language`）照它：英文 `ENG`、簡中 `CHI`、日文 `JPN`、韓文 `KOR`，繁中不帶（綠界預設）；品項名稱（`ItemName`、`TradeDesc`）也照網頁語言。付完回到同一語言的支持頁（OrderResultURL 是 `ecpayReturn/<語言>`）。英文頁的金額寫「NT$100 (about US$3)」，約略美金寫死、不接匯率；各語言都寫明只接受台灣發行的卡（綠界個人賣家不支援國外卡，Apple Pay 裡綁的卡也一樣），以台幣扣款。
  - 計入進度：`ecpayNotify` 先驗 CheckMacValue、確認特店編號，`RtnCode` 是 `1`、不是綠界後台的模擬付款（`SimulatePaid=1`），而且金額和訂單一樣，才交給 `recordPayment`（和商店付款同一個地方）加進當月；同一張訂單通知幾次都只算一次。金額扣掉通知上的手續費（`PaymentTypeChargeFee`）；通知沒帶就算全額並記 log。付款失敗、金額和訂單不符都不算，記 log；訂單已經被清掉（超過 3 天）的付款照通知上的金額算，因為通知有我們的金鑰簽章。判斷只看背景通知，付款人回來的那一下只決定支持頁顯示哪句話。
  - 不記付款人：卡號、email 都留在綠界（沒有要 `NeedExtraPaidInfo`，通知裡也沒有卡號）；後端只記金額、時間、綠界的交易編號和付款方式。訂單號碼（MerchantTradeNo，最多 20 個英數字）由後端產生。
  - 不用登入，所以 `ecpayStart` 全站每小時最多開 60 張訂單，超過請對方晚點再試；沒付款的訂單 3 天後由 `fundingDaily` 刪掉。
  - 金流接上之前，網站的支持頁寫「線上支持即將開放」，沒有按鈕，但寫出付款方式（信用卡、Apple Pay）、新台幣金額和退款說明，不寫是哪家金流，讓金流審核看得到網站以新台幣標價（`build-site.mjs` 預設 `--payments off`），網頁版 App 也沒有支持的入口，`ecpayStart` 也因為沒有金鑰而不開單。接上的步驟見 `docs/firebase-setup.md`〈線上支持〉。隱私權政策（3.13 節、第 5 節）和服務條款（第 3 節）講綠界的段落放在 `payments:on` 裡，跟著同一個開關出現。
  - 退款：在綠界後台手動退。退款不會通知後端，所以營運者在平台後台「雲端費用 → 扣回一筆退款」填特店訂單編號，整筆從付款那個月扣回（可復原；同一筆再填一次只說已經扣回過，不給復原，免得把真的退款加回去），公開的進度只算真正留下的錢（林後 8:20–21）。
  - TODO：每月支持（信用卡定期定額）是綠界 AIO 的另一種參數，這次不做。要做時每期的授權通知一樣交給 `recordPayment`。
- **雲端費用進度**：支持頁的「這個月的支持」顯示這個月收到多少支持、目標是這個月的雲端費用（下面「每個月用在哪裡」列出每一項），所有同工看到同一組數字，有人支持就即時更新。
  - 收入自動算：Apple 的 App Store Server Notifications、Google 的 Real-time Developer Notifications、網站線上支持的綠界付款通知都通知後端，後端驗證交易後換算成台幣，加進當月。退款（含部分退款）自動扣回，退款被撤銷時加回；退款比付款先到也一樣。後端只記金額、商品、時間，不記帳號或名字（ID 是商店的交易編號，只有商店後台查得到買家）。家人共享不算付款。
  - 換算：Google 直接給開發者實收（`developerRevenueInBuyerCurrency`）。Apple 只給售價，用「售價 ÷（1＋當地營業稅）×（1－15%）」估算實收；營業稅表沒列的地區當 10%，寧可少算。外幣用每天更新的匯率（Exchange Rate API，支持頁註明來源）換成台幣，每筆收入換算後就固定，之後匯率變動不影響已收的數字。匯率超過 7 天沒更新會記錯誤 log。
  - 支出由平台營運者在平台後台手動填：每項寫名稱、金額、台幣或美元、每月或每年。每年的項目除以 12 攤到每個月。這個月的目標 = 各項換算成每月的總和。
  - 結餘：每個月收到的超過目標，多出來的留到下個月；不夠的由平台營運者補上，不會變成之後月份的欠款，畫面上也不顯示還差多少。還沒設費用、或某月換不到匯率時，那個月的目標當 0，收到的錢全部留到下個月。
  - 畫面：進度條是「這個月可用（本月收到＋前幾個月的結餘）÷ 這個月的目標」。超過目標時，再顯示多出來的錢還能維持幾個月（多出來的 ÷ 目標，取整數）。
  - 測試付款不算：prod 只接受 Apple 正式環境的通知、dev 只接受 sandbox；Google 的測試購買直接略過；綠界的測試環境只能在 dev 用，prod 只接正式環境。Google 訂單 3 天還沒結算就放棄並記錯誤 log。

## 實作方式

- **重寫**，不搬 self-host 的畫面、流程、狀態管理與資料存取。self-host 的程式碼與註解當規格讀：每張 ticket 先列出舊版的行為與邊界情況，再重新設計。
- 只有不碰 UI、不碰 Firebase 的純邏輯（同工排序、匯入解析、日期工具）可以搬，搬時補測試；新設計下不合理就重寫。
- Firebase 專案用 Hans 的**個人 Google 帳號**建立，不放在 dwave.cc organization 底下。

## 效能

目標：比 self-host 版明顯順。self-host 在資料一多時幾乎都會卡。

self-host 已經做了延遲建構清單（`ListView.builder`）和縮小重建範圍（`context.select`），所以卡頓的主因推測是下面兩點，M2 先用大量測試資料實測確認：
- Flutter Web 在 iPhone 上只能跑 JS 版 CanvasKit，Dart 全擠在 UI 執行緒；wasm 版被 WebKit bug 擋住（Android 的 Chrome 從 2026-10-11 起跑 wasm 版，見量測紀錄）。
- 每次進畫面都向伺服器重讀（`.get()`），打開選人視窗就重抓全部使用者。

做法：
1. iPhone 使用者以原生 App 為主，這是最大的改善。
2. 資料層：開 Firestore 離線快取；改用 listener，先用快取顯示，再背景更新；成員名單每間教會只讀一次，在記憶體共用。
3. 卡片內容（服事項目、特別活動）也延遲建構；排序、分組這類計算放在 build 之外，資料變了才重算。
4. 驗收目標，每個里程碑用測試資料實測（150 位同工、一年份服事表），在原生 App 與 iPhone Safari 各測一次：
   - 原生 App 冷啟動到看見服事表 < 1.5 秒。
   - 切換頁面、打開選人視窗 < 100ms。
   - 捲動維持 60fps。
5. Web 版的引擎限制無法消除，但資料層的改善一樣適用。

條件：

解讀：
- 這台機器沒有 GPU，瀏覽器的 WebGL 是軟體繪圖，所以捲動 fps 和 iPhone 不能直接比。冷啟動、切換分頁、選人在這種條件下都在目標附近。
- 選人視窗在 WebKit 超過 100ms，主要花在底部面板第一次排版。已經把搜尋比對改成每個名字只正規化一次。
- 捲動時最長的那一格，發生在第一次畫出新的中文字的時候：Web 版的中文字型是執行時才從 Google Fonts 下載的。
- Web 版首頁、登入頁與直接開啟教會網址時，先預熱首畫面及必要帳號／教會狀態文字的字型，不等管理、匯入等未開啟畫面的文字；已辨識的服事表與教會資訊深連結也只加上目的頁文字（第三批），其他初始深連結仍預熱全部 App 文字。載入畫面從第一個非 loading 狀態起最多等字型 3 秒，切換路由不重新計時；首個目的頁面（或可重試的下載錯誤頁）畫出來後才拿掉。接著才預熱常用約 4300 字的 20 個字型檔（共約 740 KB），不與首畫面競爭；未預熱的動態名字與互動後文字由引擎按需下載。只對繁中（zh-TW）瀏覽器有效，其他語言引擎會選別的字型。
- 教會頁面（`/c/ID`）和它的 manifest 由 churchPage 函式產生，閒置後第一次呼叫要冷啟動 4–13 秒，這段時間整頁空白。教會頁面對每個人都一樣，回應加 `s-maxage=86400`，讓 Hosting 的 CDN 存一天：從主畫面打開不必等函式。manifest 照瀏覽器的語言，不給 CDN 存：Hosting 轉給函式的 `Accept-Language` 只剩語言（zh-MY 變 zh），CDN 也照這個分，分不出簡繁；瀏覽器原本的在 `x-orig-accept-language`，函式讀這個。`firebase.json` 全站 `no-cache` 的規則因此不含 `/c/`（Hosting 的 header 設定會蓋掉函式自己給的）。改教會名稱或 logo 最多一天才看到；Hosting 部署會清掉 CDN。邀請連結要即時檢查邀請，不存；第一次點仍可能冷啟動，上線時再看要不要讓正式站常駐一台（`minInstances`）。
- 字型檔（圖示字型每次 build 都只留用到的圖示）部署前改成帶內容 hash 的檔名，快取一年；不然手機留著舊的圖示字型，新的圖示會是空白。

- 行事曆 agenda 的 lazy sliver 原型減少首幀建構，但不等高活動使月底日期定位失準。撤回 production 原型，留下 480 筆不等高活動的公開導航回歸；可靠方案要真正 indexed positioning，不用省建構交換導航正確性。原型 profile 計時有本機併發干擾，只作探索性證據，不列為交付成績。
- 同 query 的單 instance flight 原型可合併上游，但跨 instance 寫入後仍可能回填舊活動，須 durable query／write revision 才能鎖住；本批不增加 schema、讀寫或改快取失效語意，所以未保留。
- 不開 Wasm、不大量 preload、不設定付費 minInstances，未部署或操作真實資料。

**2026-10-11：Chrome／Android 改跑 wasm，網頁版不再下載 Google 登入 SDK**

- Wasm：部署改成 `flutter build web --wasm`。Flutter 的 loader 只在 Chromium 系瀏覽器（Chrome、Android 的 Chrome、Edge）用 wasm 版；Safari 與 iOS 上所有瀏覽器仍被 WebKit bug 267291 擋住（2026-09 仍未修），Firefox 也還不行，這些照舊跑 JS 版，同一份部署自動選。self-host 時期沒加 wasm，是因為使用者以 iPhone 為主、加了換不到東西；現在 Android 使用者跑 wasm 會快。
- 固定單執行緒 skwasm：多執行緒需要 COOP/COEP（cross-origin isolation），會擋掉 Google 登入彈窗；Flutter 3.47 的多執行緒 skwasm 也有文字畫面當機的問題（flutter/flutter#190039）。
- 代價：dart2wasm 目前不拆 deferred 程式（3.50 才有實驗選項），Chrome 上第二批的「打開才下載」不再適用；這已算在下面的數字裡。部署多一份 wasm 產物，App 殼更新時整版下載也多約 1.3 MB。
- wasm 下 JS interop 的 `is`／`as` 行為不同：自己的 interop（`app_update_gateway_web.dart`、`push_clicks_web.dart`）都是先 `dartify()` 再用 Dart 的 `is` 判斷，兩種編譯結果一樣，不用改。
- Google 登入 SDK：網頁版登入一直走 Firebase 彈窗，`google_sign_in` 只有原生 App 用。`app/packages/google_sign_in_unused_web` 取代 web 實作，不載入任何東西、被呼叫就拒絕；原生 App 不受影響，不 fork 上游套件。

量測：demo release build（PERF_MARKS），Mac 上的 headless Chromium，Android UA、393×852、DPR 2、CPU 降速 4×、延遲 150ms，伺服器像 Hosting 一樣送 Brotli；每個情境三版交錯 6 輪取中位數，計時從開始載入到首頁畫出來（`[perf] home-visible`）。不是實機成績。

| 情境 | JS 版 | wasm 版 | 不載 Google 登入 SDK |
| --- | --- | --- | --- |
| 首次開啟，4 Mbps | 7.48 秒 | 7.44 秒 | 7.48 秒 |
| 首次開啟，20 Mbps | 3.27 秒 | 2.78 秒 | 3.25 秒 |
| 重開（檔案已快取） | 0.96 秒 | 0.64 秒 | 1.06 秒 |

解讀：慢網路時三版都卡在下載約 3 MB；網路夠快或檔案已快取時，wasm 版明顯快（重開 −33%）。Google 登入 SDK 本來就不擋首畫面，拿掉後時間沒有可量的差別，只是每次啟動少一個第三方連線、少約 100 KB。wasm 版的瀏覽器 e2e（登入、建教會、排服事、邀請、加入、設牧區）通過；打包後的 release 在 Chromium 載入帶 hash 的 wasm 入口、App 殼只快取 wasm 那組並能離線開啟，WebKit 則載入 JS 版、只快取 JS 那組。

**2026-10-12：只帶繁中的 Flutter 內建文字（#70）**

- Flutter 內建文字（按鈕、日期選擇器、無障礙標籤）原本用 `GlobalMaterialLocalizations.delegate` 等三個 delegate，它們依語言挑翻譯，所以 80 幾種語言和每個語言的日期資料都打包進去。改成 `app/lib/core/builtin_localizations.dart` 只建 App 有的語言那幾份，日期資料也只從 Flutter 複製那幾種（`date_data.dart`，測試比對兩者相同）。
- JS 版 `main.dart.js`（prod config）：未壓縮 4.56 MB → 3.96 MB，gzip 1,266 KB → 1,148 KB（−118 KB，約 9%）。
- 日期選擇器原本拿到 `zh` 的日期格式（周日），現在和 App 自己的日期一樣用 `zh_TW`（週日）。`Intl.defaultLocale` 跟著目前的語言：App 自己的 `DateFormat` 都不指定語言，跟著畫面的語言走。

參考官方 guideline：[Flutter 效能](https://docs.flutter.dev/perf/best-practices)、[Web profiling](https://docs.flutter.dev/perf/web-performance)、[Firestore](https://firebase.google.com/docs/firestore/best-practices)、[Functions](https://firebase.google.com/docs/functions/tips)、[resource hints](https://web.dev/learn/performance/resource-hints)、[Safari Web Inspector](https://developer.apple.com/safari/tools/)。
