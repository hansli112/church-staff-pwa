# 服事表圖片轉 JSON 的 prompt（模板）

**這是模板，不要直接用。** 裡面的 `{{...}}` 要由
`scripts/build-import-prompt.py` 從 Firestore 填進去，產生的成品會寫到
`.local/`（已 gitignore）。

這個 repo 是公開的，所以同工姓名、綽號對照一律不寫在這裡。
下面範例裡的人名都是虛構的。

## 怎麼用

**在 app 裡按「JSON 匯入」→「從照片辨識」，選服事表照片就好。**
辨識結果會填進下面那個文字框，看一眼再按匯入。

app 送到 `POST /api/roster/import-image`，那支
（`functions/api/roster/import-image.js`）組出 prompt，連照片一起送給
Gemini，把結果原樣回傳。**它不做任何驗證** —— 名字比對、日期範圍、匯入結果
那份報告全都還在 `parseRosterImportJson`，也就是手動貼上走的同一條路。
辨識只是省掉打字，不是另一條匯入流程。

### prompt 分成兩半

| | 是什麼 | 什麼時候變 | 誰來填 |
|---|---|---|---|
| **模板** | 版面規則、欄名對照、綽號、敬拜團展開 | 有人去改 `.local/import-rules.json` 才變 | `--publish` 寫進 `settings/import_prompts` |
| **現況** | 服事項目、活動清單、同工名單、今天 | 管理員在 app 裡動一下就變 | worker **每次呼叫**現場讀 Firestore |

所以 **新同工建完帳號就直接生效**，服事項目、活動選項新增也一樣 ——
不必有人記得回來重跑腳本。

會這樣拆是因為第一版把名單烤進發佈的 prompt 裡，結果每來一個新同工就要有人
記得跑一次腳本。沒有人會記得。

### 只有改了規則才要重新發佈

```
python3 scripts/build-import-prompt.py --publish
```

改了 `.local/import-rules.json`（版面規則、欄名對照、綽號）或模板本文之後跑。
**動名單、服事項目、活動選項都不用跑。**

`settings/` 的寫入權限在 firestore.rules 裡是 admin only，但這支腳本用的是
GCP 憑證（專案 editor 以上），走的是 IAM 那條路、不經過 rules。

模板裡剩下的 `{{...}}` 必須剛好等於 worker 會填的那幾個 —— 對不上的話腳本會
當場停下來，而不是發佈一份帶著 `{{NAMES}}` 字面值的 prompt 上去。

### 需要設定的東西

Cloudflare Pages 的**執行期**環境變數 `GEMINI_API_KEY`（見 `.env.example`）。
放錯區會被編進前端 bundle，等於公開。

### 匯入前想先確認（人在這台機器前時）

```
python3 scripts/preview-roster-import.py <崇拜類別> <json 檔>
```

這支會抓 Firestore 現況、產生一支暫時的 Dart 測試去呼叫 app 真正在用的
`parseRosterImportJson`，印出按下匯入會看到的結果 —— 哪些名字對不上、
哪幾天不在範圍內、每天的項目排序。跑完自動刪掉那支測試。

## 在本機直接試 Gemini

```
python3 scripts/try-gemini-import.py youth 服事表.jpg --preview
```

跟 app 那條路用的是同一份 prompt 與同一個 parser，只是跑在本機，而且轉完
立刻接上乾式匯入。改了 prompt 規則之後要驗，用這支比開瀏覽器快。
需要 AI Studio 的 key，放 `.local/gemini-api-key` 或 `GEMINI_API_KEY`。

差別只有一個：它用 `.local/` 那份本機填好的，app 用的是 Firestore 上發佈過的
模板再現場填。填的邏輯兩邊各一份（Python 的 `fill_live`、JS 的 `fillPrompt`），
**輸出必須一模一樣**，否則本機驗過的跟線上跑的不是同一份 prompt。

改完規則記得 `--publish`，不然只有本機是新的。

## 還有一條路：claude.ai

```
python3 scripts/build-claude-skill.py
```

產生 `.local/claude-skill/roster-import.zip`，上傳到 claude.ai 的技能設定，
之後在那邊附照片說「轉 json」，把結果貼回 app 的匯入框。

app 內建辨識之後這條就不是主要流程了，留著當後路 —— Gemini 掛掉、額度用完、
或想換個模型看看結果差多少的時候還用得上。名單有異動一樣要重跑再上傳覆蓋。

⚠ 不管哪一條路，送出去的都包含完整同工名單與整張服事表。AI Studio 免費層
Google 會用送進去的資料改善產品；付費層不會。上傳到 claude.ai 也是同一個
判斷題。

## 為什麼要把名單填進 prompt

app 的姓名比對有三層。前兩層是精確比對：先找一模一樣的，找不到就找「名單裡
以這個字串結尾、而且只有一個人符合」的。這兩層錯一個字就是查無此人。

中文名字常有罕用字，而那正是 OCR 最容易認錯的地方。所以有第三層
（`_nearMatches`）：名單裡只差一個字的那幾位會被列出來當提示 ——
**但不會自動套用**。名字照表上原文寫進服事表，uid 一個都不帶。

### 為什麼不自動接回去

拿真實名單量過（53 人）：

- 名單內部互相拼錯一個字時，唯一對到「別的真人」的次數是 **0**。
- 但會落進這一層的幾乎都是**還沒建帳號的人** —— 新同工、外來講員。
  而他們的名字常常跟某個真人只差一個字：表上寫的人名單裡沒有，但名單裡
  有個只差最後一個字的另一位，候選還唯一。

自動接的結果是：陳志豪的服事被記到陳志明頭上、連上陳志明的 uid，提醒發給
陳志明，而「陳志豪」這個名字從表上整個消失。**兩邊都不會知道。**

所以第三層只提示。匯入結果會寫成

```
名單裡沒有這個人
  ・陳志豪（名單裡有很像的：陳志明）
```

要不要改那一格由人決定。**真正該做的還是讓模型根本不要拼錯字** ——
prompt 裡附上完整名單當白名單，讓它只能從裡面挑。

**忘了重新產生也不會壞** —— 新同工不在名單裡時，LLM 會照表格原文輸出，
app 那邊的後綴比對照樣接得住。名單過期只會讓**新來的那幾位**退回舊模式。

## 模板本文

````
幫我把服事表照片轉成 JSON。只輸出 JSON，不要有任何說明文字，
不要用 markdown 的程式碼圍欄包起來。第一個字元是 [，最後一個字元是 ]。

## 只要這些

日期、服事項目、同工、活動。其他一律不要。
{{LAYOUT_RULES}}
## 服事項目命名

只能用以下名稱，一字不差：
{{ROLES}}

清單裡沒有的欄位整欄不要輸出。
{{EXTRA_ROLE_RULES}}

## 人名

**輸出的人名必須是下面同工名單裡的其中一個全名，一字不差。**
表格上寫的是簡稱（去掉姓氏）或加了稱謂，你要把它還原成名單裡的全名。

同工名單：

{{NAMES}}

規則：

- 表格上的「小明」「小明哥」「陳小明」都要輸出成「陳小明」。
  稱謂有這些：哥／姐／姊／兄／弟／妹／弟兄／姊妹／牧師／傳道／師母／
  長老／執事／老師／主任。「陳大明牧師」要還原成名單上的「陳大明」。
- 中文名字有很多罕用字，照片上可能看不清楚或容易認錯。
  **不要自己拼字** —— 從名單裡挑字形最接近的那一個。
- 一格有多個人就拆成多個元素。表格用「/」或「+」分隔的都算多人，
  例如「小明/大華」→ ["陳小明", "林大華"]。
- **people 照表格上寫的先後順序，不要重排**（不要照筆畫、不要照名單順序）。
  寫在前面的通常是主要負責的人，app 會照這個順序排每一週的名單。
- 空白格代表這一項還沒排到人 → "people": ["待定"]。「待定」照寫，不用對名單。
- 「暫停」不是人名，代表那週沒有這一項 → 整個項目不要輸出，
  不可以寫成 ["暫停"]。
- 真的對不到名單裡任何一位（例如新同工還沒建帳號），就照表格原文輸出，
  不要硬塞一個名單裡的人。
{{NICKNAMES}}
{{TEAM_RULES}}
## 活動

放進該天的 `events`。哪些格子算活動，見上面「這張表怎麼讀」。

規則：

- 意思相同的話，優先用下面這幾個既有名稱，一字不差：
  {{EVENTS}}
- 對不到既有名稱的就照表格原文一整串抄，**不要拆**。
  合併儲存格裡的「活動名稱/地點」是一個名稱，那個「/」不是分隔多人的意思。
- 同一天有多個活動就放多個元素；同一天不可以有重複的活動名稱。
- **不要輸出顏色。**
- 那一天沒有任何活動的話，**整個 `events` 欄位不要寫**（不要輸出 `[]`）。

## 不要輸出的欄位

- 表格下方的提醒、標題、經文、季主題。
- 表格下方那種「敬拜/某某、招待/某某」的負責人清單。那是各項的聯絡人，
  不是某一週的服事。

## 格式

[
  {
    "date": "2026-07-04",
    "duties": [
      {"role": "{{SAMPLE_ROLE_A}}", "people": ["陳小明"]}
    ],
    "events": ["夏令營/營地"]
  },
  {
    "date": "2026-07-11",
    "duties": [
      {"role": "{{SAMPLE_ROLE_A}}", "people": ["陳小明", "林大華"]},
      {"role": "{{SAMPLE_ROLE_B}}", "people": ["待定"]}
    ]
  }
]

- `date` 一定是 `YYYY-MM-DD`。不可以寫 `2026/07/11` 或 `7/11`。
- 年份：標題有寫就照它（例如「2026 年 7-9 月份」）。**標題沒寫年份的話**，
  今天是 {{TODAY}}，挑一個讓表上那幾個月份離今天最近的年份。
  年份猜錯整份都匯不進去，而表上通常只有月和日，所以這條要特別小心。
- `people` 的每個元素都必須是字串。不可以出現 null、數字。
- `duties` 不可以是空陣列。那天完全沒有服事就不要寫 `duties` 這個欄位。
- 每一天至少要有 `duties` 或 `events` 其中一個，兩個都沒有就整天不要輸出。
- 同一個日期只能出現一次。
- duties（服事項目）之間的排列順序不重要，匯入後會自動照服事項目設定重排。
  但每一項裡 people 的順序很重要，見上面「人名」。

## 輸出前自我檢查

1. 每個 date 都是 YYYY-MM-DD，而且沒有重複。
2. 每個 role 都在上面的命名清單裡，一字不差。
3. people 裡的每個名字都在同工名單裡找得到一模一樣的，或是「待定」。
   沒有 null、沒有數字、沒有「暫停」、沒有哥姐。
4. 沒有空的 duties 陣列、沒有空的 events 陣列。
5. 同一天的 events 沒有重複的名稱。
6. 輸出的第一個字元是 [，最後一個字元是 ]，前後沒有其他文字。
````

## 各崇拜的差異怎麼設定

服事項目與活動清單由腳本從 Firestore 的 `settings/roster_templates`、
`settings/event_options` 讀出來填入，不必手動維護。

各教會自己的規則放在 `.local/import-rules.json`，每個崇拜一個鍵：

```json
{
  "youth": {
    "layoutRules": "## 這張表怎麼讀\n\n一列一天，服事項目在最上面那一列。...",
    "extraRoleRules": "- 表格的「會前禱+奉獻」是一欄，要拆成兩項：會前禱告、奉獻教導。\n  同一格的人兩項都填。",
    "teamRules": "## 敬拜團\n\n敬拜團那一欄寫的是團名，實際人員在表格下方的說明列。...",
    "nicknames": { "小名": "陳小明" }
  }
}
```

| 鍵 | 放什麼 |
|---|---|
| `layoutRules` | **這張表的版面怎麼讀。** 見下一節 —— 這是三個崇拜差最多的地方 |
| `extraRoleRules` | **欄名 → 服事項目的對照表**，以及一欄要拆成兩項之類的特例 |
| `teamRules` | 團名要展開成個別人員的規則 |
| `nicknames` | 跟本名沒有共同字、只能查表的綽號 |

沒有這個檔案的話那幾段都留空，其餘照常產生。

### 為什麼一定要寫欄名對照表

`{{ROLES}}` 只說了「可以用哪些名稱」，沒說表上那一欄是哪一個。三張表的欄名
都跟服事項目名稱不一樣：

| 表上寫 | 服事項目 | 哪張表 |
|---|---|---|
| 敬拜 | 敬拜主領 | 主日、兒主 |
| 講道 | 信息 | 主日 |
| 導+錄 | 導播（**一項**，服事項目裡沒有「控機」） | 主日 |
| 配唱 | Vocal | 兒主 |
| 木箱 | 鼓 | 兒主 |
| 會前禱+奉獻 | 會前禱告 ＋ 奉獻教導（拆兩項） | 青崇 |

沒有這張對照表，模型得自己猜「木箱」是「鼓」。猜錯那一欄整個對不上，而且
**不會有人發現** —— app 只會說「沒有設定這個服事」，看起來像是同工的設定
漏了，不像是整欄接錯。

### 差一個罕用字的寫法要寫進綽號對照

表上寫「雅亭」而名單上是「黃雅婷」、寫「佳容」而名單上是「陳佳蓉」——
差的都是罕用字，而且去掉姓氏後只有兩個字，後綴比對接不住
（`黃雅婷` 不以 `雅亭` 結尾）。第三層會把它們列成提示，但不會自動套用，
所以**這類要寫進 `nicknames`**，讓模型直接輸出全名。

對不出來的就不要寫。「佳芸」跟「陳佳蓉」（佳吻合）與「林淑芸」（芸吻合）
都只差一個字 —— 這種留給第三層把兩個候選都列出來，由人決定。

名單裡本來就可能有幾組人互相只差一個字（兄弟姊妹、同一個名字字根）。
那幾組的提示會一次列出兩位，不挑。

### 為什麼版面規則一定要各崇拜各寫一份

原本這幾條結構規則寫死在共用的模板本文裡，假設「一列一天」。實際上三張表
差到不能共用，而共用的版本對其中兩張是**錯的**，不只是不足：

- **主日是轉置的** —— 日期在最上面那一列，服事項目在最左邊那一欄。
  共用版本講的「表格右側時段欄位」「橫跨多欄的合併儲存格」在這張表上
  根本不是那個意思：跨多欄在這裡是跨多個**日期**。
- **主日右邊那塊自己寫了日期的活動要收進來**（「孩童奉獻禮：11/29」），
  但共用版本有一條「格子裡自己寫了另一個日期的欄位整欄略過」，那是為了
  青崇的「週二禱告會」欄寫的 —— 兩張表對「自己帶日期」的處理正好相反。
- **兒主的「回應」「小組」欄是整季合併成一格的**，意思是整季固定的分組，
  不是每週輪的服事，所以整欄不要。共用版本只有「橫跨多欄＝常規服事被活動
  取代」，方向與語意都不對。

所以模板本文只留跟版面無關的部分（服事項目命名、人名還原、格式、自我
檢查），版面那段換成 `{{LAYOUT_RULES}}`，各崇拜自己寫。

## 活動顏色

prompt 刻意不輸出顏色。顏色設在 app 的「事件選項設定」，名稱一樣就會自動套用。

不在事件設定裡的活動還是會標上去，只是沒有預設色，並列在匯入結果的
「活動沒有固定顏色」。管理員可以在那一段直接按「加入活動清單」，顏色會
自動挑一個這個崇拜用得最少的；已經匯入的那幾天也會跟著變色，不必重匯。

## 匯入後會看到什麼

app 匯入完會跳出「匯入結果」。裡面列的名字**都已經寫進服事表了**，
列出來是讓你知道，不是要你回去改 JSON：

- **沒有設定這個服事** — 人在名單上，只是沒設定這一項（臨時支援很正常）。
  真的多了固定班底才需要按「新增服事至同工」。
- **外來講員** — 只排在「信息」、名單裡沒有、也沒有很像的人。名字照樣寫進
  去了，講員沒有帳號是正常的，所以一行帶過，不算問題。名單裡有很像的
  名字就不算講員（多半是同工的名字被讀錯一個字），會留在下一段。
- **名單裡沒有這個人** — 名字有排上去，但沒有帳號就收不到服事提醒。
  後面括號裡的「名單裡有很像的」是提示，**名字沒有被換掉**。確定是同一位
  就把它加進 `.local/import-rules.json` 的綽號對照，下次匯入就會直接對上。
- **不確定是哪一位** — 名單裡有兩個人的名字都對得上，這一格沒有連到帳號。
- **這幾天沒有匯入** — 服事表裡沒有那幾天。app 只產生本季與下季。
  主日表旁邊寫在星期六之類的活動不會落到這裡：主日的版面規則會把它放到
  活動之後最近的那個主日，名稱後面帶上它自己的日期（「感恩聚餐（12/26 六）」
  放進 12/27）。放之後是因為 app 只顯示還沒過的服事表，放在之前那個主日，
  活動當週就看不到了。
- **活動沒有固定顏色** — 活動標上去了，只是沒有預設色。管理員可以直接按
  「加入活動清單」。名稱帶著自己日期的一次性活動（「感恩聚餐（12/26 六）」）
  不會列在這裡：名字每次都不同，加進清單也對不上下一次。
